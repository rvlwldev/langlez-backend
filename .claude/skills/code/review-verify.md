# 리뷰B: 실행 검증

이 PR의 배경을 모르는 상태에서 PR 본문(계획)의 완료 조건과 테스트 시나리오를 기준으로 판단한다. 추측하지 않는다. 모든 판단은 직접 실행한 결과로 뒷받침한다.

## 할 것

1. `gh pr view <번호>`, `gh pr diff <번호>`로 계획과 변경을 읽는다.
2. 완료 조건과 테스트 시나리오마다 그것을 검증하는 테스트가 있는지 대조한다.
3. 빠진 엣지 케이스를 찾는다: 경계값, null과 빈 값, 잘못된 입력, 동시 호출, 외부 시스템 실패(DB, Redis, Kafka, Mongo 끊김), 트랜잭션 롤백, 인증 없는 요청.
4. 직접 실행한다.
   - 변경된 모듈의 테스트: `server/`에서 `./gradlew :<모듈>:test`
   - 의심되는 엣지 케이스는 임시 테스트(Kotest `BehaviorSpec`, 필요하면 Testcontainers)를 써서 돌려 본다.
   - HTTP 동작은 가능하면 앱을 띄워 실제 요청을 보낸다 (`docker/start.sh`, `./gradlew :app:bootRun`, `curl`).
5. 항상 통과하는 테스트, 구현 세부에 묶인 테스트가 있는지 본다.

## 규칙

- PR의 코드를 고치지 않는다. 임시 테스트는 확인한 뒤 지우고, 띄운 프로세스도 정리한다. 끝날 때 `git status --porcelain`이 비어 있어야 한다.
- 지적마다 시나리오, 실행한 명령, 실제 결과(출력 발췌), 기대 결과를 적는다. 실패를 재현한 임시 테스트는 코드를 코멘트에 붙여 구현자가 가져다 쓰게 한다.
- 실행하지 못한 것은 "확인 못 함"과 이유를 적는다. 확인하지 못한 것을 통과로 치지 않는다.
- blocking: 완료 조건 미충족, 재현된 버그, 계획의 시나리오에 대응하는 테스트 없음. 나머지는 제안이다. blocking이 하나라도 있으면 `CHANGES`다.

## 보고

PR 코멘트 하나로 남긴다.

```
gh pr comment <번호> --body-file - <<'EOF'
## 리뷰B: 실행 검증
...
VERDICT: APPROVE
EOF
```

마지막 줄은 `VERDICT: APPROVE` 또는 `VERDICT: CHANGES`다.
