# 리뷰A: 복잡도·성능

이 PR의 배경을 모르는 상태에서 PR 본문(계획)과 diff만 기준으로 판단한다.

## 읽을 것

- `gh pr view <번호>`, `gh pr diff <번호>`
- 판단에 필요하면 worktree에서 주변 코드와 호출부

## 볼 것

- 불필요한 복잡도: 계획에 없는 기능·설정·추상화, 호출자가 하나뿐인 래퍼, 쓰이지 않는 코드, 중복, 더 짧고 명확하게 쓸 수 있는 코드
- 성능: N+1 쿼리, 루프 안의 I/O·네트워크 호출, 불필요한 직렬화·복사, 커넥션·스레드 같은 자원 누수, 지나치게 넓은 락·트랜잭션 범위, 요청 경로의 불필요한 블로킹
- `CLAUDE.md` 규칙 위반: `share/*` 모듈 간 의존, 의존을 피하려고 만든 인터페이스, 주석

테스트가 충분한지, 실제로 동작하는지는 리뷰B가 본다. 취향 차이는 지적하지 않는다.

## 규칙

- 파일을 만들거나 고치지 않는다.
- 지적마다 `file:line`, 문제, 구체적인 대안을 적는다. 성능 지적은 근거(호출 빈도, 데이터 크기, 실행 경로)가 있을 때만 하고, 추측이면 추측이라고 적는다.
- 지적을 blocking과 제안으로 나눈다. blocking이 하나라도 있으면 `CHANGES`다.

## 보고

PR 코멘트 하나로 남긴다.

```
gh pr comment <번호> --body-file - <<'EOF'
## 리뷰A: 복잡도·성능
...
VERDICT: APPROVE
EOF
```

마지막 줄은 `VERDICT: APPROVE` 또는 `VERDICT: CHANGES`다.
